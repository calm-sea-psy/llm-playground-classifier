## 평가 절차

1. **샘플 준비**: 실제 업무 문서(또는 X-ray) 30~150장. 정답이 있으면 정확도까지, 없으면 검증 통과율과 속도로 비교합니다.
2. **실험**: "모델 비교" 화면에서 조합(모델, OCR 경로, VLM 폴백 등)을 최대 4개 정해 실행합니다.
3. **결과 해석**: 조합별 점수와 함께 **사람이 확인해야 하는 비율**과 **틀렸는데 통과한 건수**를 봅니다. 문서별 표에서 조합마다 결과가 다른 문서를 열어 원인을 확인합니다.
4. **오답 분류**: 틀린 이유를 나눕니다.
   - OCR이 잘못 읽음: 전처리나 규칙으로 보정. 예: PaddleOCR 줄 방향 보정이 똑바른 영수증 줄을 180° 뒤집어 읽어("1,000" ➔ "000'1") LLM 이 날짜를 지어냄 ➔ 옵션을 끄고 같은 150장으로 재측정 (아래 "사례")
   - 용어·정의를 모름: 필드 정의나 용어집(키워드 트리거, RAG의 가장 단순한 형태) 추가
   - 규칙을 알려 줘도 어김: 모델 교체, 그래도 안 되면 파인튜닝 검토
   - 정답 기준이 다름: 명세를 결정
5. **개선과 재실험**: "프롬프트" 화면에서 지시문이나 용어집을 고쳐 새 버전으로 적용한 뒤 같은 샘플로 다시 실험합니다. 작업마다 쓴 프롬프트 버전이 기록됩니다.
6. **적용**: 가장 나은 조합을 **[기본으로 적용]** 해서 실제 처리 화면의 기본 설정으로 씁니다.

자기 회사 문서로 평가할 때 정답 데이터를 준비하는 방법은 [설치와 실행 ➔ 7. 정답 데이터](installation.md#7-선택-정답-데이터)에 있습니다.

## 평가 스크립트 (`eval/`)

화면보다 큰 규모로 돌리거나 한 단계만 따로 측정할 때 씁니다. 결과는 `eval/results/{실행 이름}/` 에 저장되고 git에서 제외됩니다. 파이썬은 OCR 서비스의 가상 환경(`src/OcrService/.venv/Scripts/python`)으로 실행합니다. CNN 관련 스크립트는 CNN 서비스의 가상 환경을 씁니다.

| 스크립트 | 하는 일 |
|---|---|
| `run_eval.py` ➔ `score_eval.py` | 문서 N장을 모델별로 API에 보내 처리하고 채점합니다. 필드·금액 정확도, 품목 F1, 지어낸 금액, 검증 통과율, 시간을 CSV와 summary.md로 남깁니다 |
| `score_ocr.py`, `ocr_variants.py`, `score_aihub.py` | OCR 엔진과 옵션을 비교합니다 (언어, 문서 펴기, 경로 A/B) |
| `fallback_threshold.py` | VLM 폴백 신뢰도 기준값을 정합니다 |
| `cnn_eval.py`, `cnn_models.py`, `cnn_models_mm.py` | CNN 후보(사전학습 vs 미세조정)를 AUC, 민감도, 특이도로 비교합니다 |
| `multimodal_eval.py` | CNN + VLM + 텍스트 추출 작업을 모델별로 돌려 소견서 요약 F1, CNN AUC, VLM 정확도, 통합 검출률을 계산합니다 |
| `summary_variants.py` | 소견서 요약 프롬프트 변형(기본 / 용어집 / 예시 / 둘 다, 용어집 새 버전은 `rag@v1`)을 개발 세트와 보류 세트로 비교하고, 바뀐 판단을 목록으로 보여 줍니다 (`--diff`) |
| `agent_eval.py` | 실험 분석 에이전트 기록(`spikes/AgentSpike run`)을 과제(`eval/agent/`)로 채점합니다. 성공률, 근거 없는 숫자, 반복 호출, 회차 간 일치 ([에이전트 평가](agent_evaluation.md)) |

## 사례: 오답을 따라가 OCR 설정 문제를 찾음 (2026-09-25)

1. **증상**: 실험 상세에서 검증 통과 97.7% 인 조합의 필드 정확도가 56.5%. IMG00090 은 검증을 통과했는데 필드 2/5
2. **원문 대조**: 작업 상세의 OCR 줄에서 `~1011-282-0 10 08991-98-80` (원래 "408-86-16530 이권형 043-287-1701~2"), `000'1` (원래 "1,000") ➔ 원본 이미지는 똑바른데 줄이 180° 뒤집혀 읽힘
3. **원인**: PaddleOCR `use_textline_orientation = true` (측정 없이 켜 둔 옵션)가 똑바른 줄을 뒤집음. 날짜 줄이 깨지자 LLM 이 형식만 맞는 날짜를 지어냈고 형식 검사는 통과
4. **측정** (`eval/ocr_variants.py` + `score_ocr.py`, 같은 150장):

| 지표 | 보정 켬 | 보정 끔 |
|---|---|---|
| KORIE 필드 값 재현율 (정답이 OCR 텍스트에 있음) | 80.2% | **84.8%** |
| KORIE 문자 오류율 | 7.56% | **4.65%** |
| 상업송장 문자 오류율 | 0.70% | **0.33%** |

5. **규칙 보강**: 날짜·시각·합계·사업자번호가 OCR 텍스트에 없으면 오류 ➔ VLM 폴백 (`FieldValidator.CheckGrounded`). 적용 전에 이전 결과로 정밀도를 확인: 텍스트 경로에서 걸린 값 13개 모두 실제로 틀림
6. **전체 재측정** (`run_eval.py`, gemma4 150장): 텍스트 단계 필드 정확도 59.7% ➔ 62.6%, 폴백 45.3% ➔ 32.7%, 통과했지만 합계 틀림 12 ➔ 9건, 작업 시간 중앙값 14.9 ➔ 13.6초

## 사례: 가설이 틀린 보정 — CNN 소견 기준값 (2026-09-25)

1. **증상** (리뷰 지적): 정상 영상에도 섬유화·결절·골절 양성이 붙고, 통합 화면 작업 대부분에 "소견서 불일치"가 붙음 ➔ 가설: 0.5 일괄 기준값이 원인, 고치면 불일치도 줄 것
2. **확인**: xrv 출력은 이미 모델의 운영 기준(op_threshs)이 0.5 가 되도록 바뀐 값. 그런데 IU 에서 양성 판정 677개 중 355개(52%)가 0.50~0.52 에 몰림. 정상 40장 중 20장에 양성 소견
3. **보정** (`eval/cnn_calibrate.py`): 2차-5 평가 120건·X-ray 실험 영상을 뺀 IU 정면 1,500장에서, 양성 30건 이상 소견은 Youden 최대, 적은 소견은 정상 영상 98% 가 음성인 값 (0.5 아래로는 내리지 않음) ➔ 섬유화 0.516, 침윤 0.532, 종괴 0.525, 결절 0.515, 흉막 비후 0.506, 기흉 0.504. 무기폐·심장비대·경화·흉수·폐부종은 0.5 가 이미 최적
4. **보정에 안 쓴 120건 전후**:

| | 0.5 일괄 | 소견별 기준 |
|---|---|---|
| 양성 소견이 붙은 정상 영상 | 20/40 | **11/40** |
| 정상 영상당 양성 소견 수 | 1.1 | **0.48** |
| 소견서 불일치가 있는 작업 | 58% | 58% |
| 불일치 중 실제 CNN 오답 | 114/123 | 114/123 |

5. **재실험**: 성인 IU 29장을 gemma4·qwen3-vl instruct × 독립/CNN 참고로 다시 ➔ 점수·VLM 판단 모두 그대로 (58셀 중 변화 0). 리뷰가 든 3744(정상인데 폐렴 의심)는 CNN 을 안 보는 독립 판독에서도 같은 판단이었음
6. **결론**: 보정은 사용자에게 보이는 잡음을 절반으로 줄였지만, 불일치를 줄이려면 CNN 자체(특히 무기폐)를 개선해야 함. 가설이 틀렸다는 것도 측정해야 알 수 있었음

## 사례: 프롬프트 버전으로 고치려다 흔들림을 발견 (2026-09-25)

1. **증상** (리뷰 지적): 통합 작업 3241 에서 소견서 결론 "No focal airspace consolidation" 인데 요약이 폐렴(경화) 있음 ➔ "폐렴: 소견서 있음 vs CNN 음성" 가짜 경보, 종합 보고서도 자기모순
2. **원인 확인**: 용어집에 이미 "'no consolidation' 처럼 부정되면 false" 가 있었음. 소견서 FINDINGS 가 개인정보 가림으로 깨져("The lungs focal airspace consolidation.") 결론과 충돌
3. **v1** (프롬프트 화면에서 저장·적용): 부정문 우선 + 부정 표현 항목 + "FINDINGS 와 결론이 다르면 결론". 평가 스크립트가 API 의 적용 버전을 읽게 함 (`rag@v1`)
   ➔ test 21 ➔ 20, dev 12 ➔ 13 (합 33 ➔ 33). 3241 은 고쳐졌지만 "No significant change in … pleural fluid"(그대로 있음)를 부정으로 오독
4. **v2**: "no significant change / unchanged / stable 은 부정 아님" ➔ test 19, dev 12 (합 31) ➔ 개선처럼 보임
5. **그런데** 같은 3241 을 API 로 돌리자 v2 에서도 폐렴 있음. 같은 입력을 두 번 부르니 결과가 달랐음 (temperature 0)
6. **흔들림 측정**: v0·v2 를 test 에서 한 번 더 (`rag#r2`, `rag@v2#r2`)

| 비교 | 판단이 다른 칸 (600칸 중) | 오답 |
|---|---|---|
| v0 1차 vs v0 2차 | 2 (3241·3396 폐렴) | 21 vs 19 |
| v2 1차 vs v2 2차 | 0 | 19 vs 19 |
| v0 2차 vs v2 2차 | 0 | 19 vs 19 |

7. **결론**: v1·v2 의 차이는 흔들림 범위 (±2건/120). 버전 효과 없음. v2 는 해가 없어 적용해 두되 파일 기본값으로 올리지 않음. 3241 같은 흔들리는 건은 "사람 확인 필요"로 걸러짐
8. **교훈**: 오답 1~2건 차이로 프롬프트 버전을 고르지 않는다. 같은 설정을 반복 실행해 흔들림부터 잰다

## 사례: 기준값 바로 위는 "경계" (2026-09-25)

통합 작업 3241 에서 CNN 심장비대 0.50(기준 0.5)이 양성 ➔ 소견서("심장 윤곽 정상")와 불일치 ➔ 종합 보고서에 "심장비대 가능성 (CNN)". 2차-5 의 120건에서 기준값 바로 위를 판단 보류로 둘 때:

| 경계 폭 | 경계 판정 | 그중 실제 양성 | 보고서에 들어가는 거짓 양성 | 불일치 있는 작업 |
|---|---|---|---|---|
| 없음 | 0 | 0 | 99 | 58% |
| 0.01 | 24 | 6 | 81 | 53% |
| **0.02** | 44 | 11 (25%) | **66** | **47%** |
| 0.03 | 63 | 19 (30%) | 55 | 43% |

➔ 0.02 채택 (`CnnFinding.Borderline`): 소견서 비교에서 빼고, 종합 보고서에는 "경계(판단 보류)"로만 전달. 화면에는 확률과 함께 "경계"로 표시. X-ray 단독 판독의 CNN·VLM 교차 검증은 실험 지표가 바뀌어 그대로 둠. 3241 재실행: 심장비대 0.501 이 경계로 빠지고 보고서 핵심 소견에서도 사라짐
