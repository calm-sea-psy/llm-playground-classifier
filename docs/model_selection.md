## 3. 해석

**정확도는 거의 같다.** 합계·세금·날짜·품목 F1은 두 모델 차이가 1~3%p(1~4건)로, 150장 규모에서는 의미 있는 차이가 아니다.

**차이는 "OCR이 틀렸을 때 어떻게 행동하느냐"에서 난다.**
- PaddleOCR은 영수증 폰트의 수량 `1`을 `7`로 자주 읽는다 (`9,980 7 9,980`)
- gemma4는 "금액 = 단가"인 줄을 보고 수량을 1로 바로잡는다 ➔ 수량 정확도 95%, 검증 통과 86%
- qwen3-vl은 OCR 값을 그대로 옮기거나(24개) 수량×단가로 금액을 새로 계산한다(5개) ➔ 검증 규칙에 걸려 폴백 65%, 최종 통과 54%
- qwen3-vl은 틀린 값을 규칙이 잡아내 "검증 통과 중 오답"은 적지만(1.2%), 절반 가까운 문서가 사람 확인으로 넘어간다

**"검증 통과했는데 합계가 틀린" gemma4 11건의 대부분은 모델 오류가 아니라 라벨 정의 차이다.**
- KORIE의 합계 영역은 할인 전 **총합계**(예: 46,140)를 가리키고, 프롬프트는 **최종 결제 금액**(결제대상금액 26,160)을 요구한다. 11건 중 8건은 두 모델이 같은 결제 금액을 냈다
- gemma4 고유 오류는 3건 (IMG00047 합계 오인식, IMG00599 할인 전/후 혼동, IMG00635 음수 부호 누락)

**라벨 정의가 모호한 필드**(모델 비교에는 공정하지만 절대 수치로 해석하면 안 됨)
- 거래 시각: 다이소 영수증에 결제 시각과 출력 시각이 둘 다 있음. 라벨은 출력 시각, 모델은 결제 시각을 고름 (두 모델 모두 65.3%)
- 소계: 매장마다 KORIE 라벨이 공급가액/할인 전 금액/합계와 같은 값 등 제각각. gemma4는 확신이 없으면 null(16건)을 내는 경향
- 영수증 번호: 거래번호·승인번호·POS번호가 섞여 있음 (15~17%)
- 상호: 라벨은 법인명 전체("(주)아성다이소_청주산남2호점"), 모델은 간판명("다이소")을 내는 경우가 많음

## 4. 선정 근거

todo 4번 ㅁ)의 기준 순서로 판단했다.

1. **필드 정확도 (특히 숫자)**: 합계·세금·날짜·품목은 동률 수준. 다만 **지어낸 금액**(1 vs 5)과 **수량 보정**(95.1% vs 90.6%)에서 gemma4가 낫다. 이 프로젝트가 VLM을 주 경로에서 뺀 이유가 "숫자 환각"이므로 가장 중요하게 봤다
2. **스키마 준수**: gemma4 100%, qwen3-vl 99.3% (1건 분류 실패)
3. **처리 시간·VRAM**: qwen3-vl이 작업당 약 6초 빠르고 VRAM 0.6GB 여유. 비동기 큐 구조라 건당 6초 차이보다 **검증 실패로 사람 확인이 필요한 문서 비율(14% vs 46%)** 이 운영 부담에 더 크다고 판단

"차이가 근소하면 속도·VRAM이 나은 쪽"이라는 기준도 검토했지만, 검증 통과율(86% vs 54%)과 지어낸 금액 수의 차이는 근소하지 않다고 봐서 적용하지 않았다.

**결론: gemma4:12b.** qwen3-vl:8b는 비교 페이지·배치 평가용으로 계속 선택 가능하게 둔다.

## 5. 부수 발견과 조치

- **OCR 처리 시간 p90 24초** ➔ 원인: 약 9백만 화소를 넘는 이미지(휴대폰 3024×4032)에서 PaddleOCR 추론이 1초 ➔ 20초 이상으로 급격히 느려짐. VRAM 경합이 아님 (Ollama 언로드 후에도 동일). 2550×3400(8.7MP) 1.0초 / 2625×3500(9.2MP) 17초
  ➔ OcrService에서 8.5MP 초과 이미지를 축소해 인식하고 bbox는 원본 좌표로 복원 (`max_pixels`). 해당 사진 22초 ➔ 1초, 평균 신뢰도 0.97 ➔ 0.97
  ➔ 위 처리 시간 표는 수정 전 측정값이다 (OCR p90이 작업 p90을 끌어올림)
- **금액 자릿수 오추출**(0단계 gemma4의 "5,270조")은 300회 실행에서 0건 ➔ 금액 문자열 스키마(`AmountsAsString`) 비교는 보류 (이후에도 쓸 일이 없어 4차 통합 때 옵션을 삭제)
- **VLM 폴백의 효과**: 텍스트 추출만 했을 때 대비 최종 결과에서 순증한 정답 필드 gemma4 19개, qwen3-vl 31개

## 6. 한계와 다음 단계

- 정답 라벨은 사람이 아닌 Claude가 작성했다. 이후 사람이 표본 30건(Claude가 OCR 값을 고친 행 20 + 그대로 둔 행 10, 필드 9종)을 검수해 **30건 모두 맞음**을 확인했다 (2026-09-24, `src/OcrService/tools/label_review.py`). 오류 0건이어도 95% 신뢰 상한은 약 9.5%(고친 행만 보면 13.9%)라, 절대 수치는 여전히 수 %p 오차를 감안할 것
- 150장·영수증 한 종류. AI Hub 상업송장·보험 청구서는 합성 데이터라 필드 정답이 없어 이번 선정에서 제외
- 프롬프트는 두 모델에 같게 고정했다. 모델별 프롬프트 튜닝 후 결과가 달라질 수 있음
- 후속 후보: 합계를 "결제 금액"과 "총합계" 두 필드로 나누기, OCR 수량 오인식 대응(서버 인식 모델 검토), 2번 의료 경로(VLM 소견서)에서 두 모델 재비교

## 후속 (2026-09-25): OCR 줄 방향 보정 끔 + 근거 확인 규칙

이 리포트의 수치는 PaddleOCR `use_textline_orientation = true` 로 측정했습니다. 이 옵션이 똑바른 영수증 줄을 180° 뒤집어 읽는 문제를 찾아 끈 뒤, gemma4:12b 로 150장을 다시 측정했습니다 (품질 개선 B 단계 이후 결과와 비교). 텍스트 단계 필드 정확도 59.7% ➔ 62.6%, 합계 90.9% ➔ 92.3%, 폴백 45.3% ➔ 32.7%, 검증 통과했지만 합계 틀림 12 ➔ 9건. 자세한 과정은 [평가 가이드](evaluation-guide.md#사례-오답을-따라가-ocr-설정-문제를-찾음-2026-09-25)에 있습니다. qwen3-vl 은 다시 측정하지 않았습니다.
