# 문서 종류 팩 측정 보고서

[README](../README.md) · [구조](architecture.md) · [설치와 실행](installation.md) · [화면 사용법](user-guide.md) · [평가 가이드](evaluation-guide.md)

문서 종류 팩(`packs/<종류>/`)을 배포용 프로그램(exe)에 넣기 전에 잰 결과입니다. 팩의 `type.json` 에 있는 `release` 가 이 문서의 절을 가리킵니다.

- **합격(passed)**: 기준을 넘음. 검증에 걸린 문서만 사람이 확인합니다.
- **조건부(conditional)**: 기준 일부에 못 미쳤지만 조건을 지키면 씁니다. 조건은 팩의 `release.conditions` 와 이 문서에 같이 적습니다.
- 이력서는 기준을 **측정 전에** 정했고, 결과를 본 뒤 바꾸지 않았습니다. 판정은 튜닝에 쓰지 않은 **보류 세트**로 냈습니다.
- `release` 가 없는 팩(상업송장 · 보험 청구서)은 평가 도구에서만 씁니다. 결과가 같은지(동등성)만 확인했고, 정확도 합격 기준으로는 아직 재지 않았습니다.

## 이력서 (resume)

**조건부 합격** · 팩 v0.2.0 · gemma4:12b · 2026-09-26

### 데이터

실제 이력서는 개인정보라 쓸 수 없어 **합성 이력서**를 만들었습니다 (`eval/digitizer/gen_resume.py`).

- 가짜 인물과 정답 JSON 을 먼저 만들고, 양식 4종(자유 · 표 · 채용 사이트형 · 경력이 많은 2쪽)으로 PDF · DOCX · 스캔 흉내(기울기 · 흐림 · 잡음)를 만듭니다.
- 표 양식에는 주민등록번호 · 가족 · 혼인 · 신장 · 본적을 넣어, 수집하면 안 되는 값이 새는지 시험합니다.
- 개발 세트 24장(팩을 고칠 때 봄) · **보류 세트 16장**(판정에만 씀, 2쪽 7장)

### 판정 (보류 세트 16장)

| 경로 | 지표 | 기준 | 결과 | 판정 |
|---|---|---|---|---|
| PDF · DOCX | 단일 필드 정확도 | ≥ 95% | 98.9% / 100% | 통과 |
| | 목록 재현율 (학력 · 경력 · 자격증 · 어학) | ≥ 95% | 100% / 100% | 통과 |
| | 지어낸 값 (원문에 없는 값) | 0 | **PDF 2건** / DOCX 0 | **미달** |
| | 수집 금지 값 누출 | 0 | 0 / 0 | 통과 |
| | 사람 확인 비율 | ≤ 30% | 12.5% / 6.2% | 통과 |
| 스캔 (OCR) | 정답 값이 OCR 텍스트에 남은 비율 | ≥ 95% | 99.3% | 통과 |
| | 단일 필드 정확도 | ≥ 90% | 99.8% | 통과 |
| 속도 | GPU 16GB, 문서당 | ≤ 30초 | 11초 | 통과 |
| | GPU 없음 (gemma-4-E4B, CPU OCR + CPU LLM) | ≤ 120초 | 중앙 64초, 최대 121.8초 (2쪽 1건만 초과) | 사실상 통과 |

- 지어낸 값 2건은 주소 동 번호 중복("110동 110동 1714호")과 빈 전공을 "-" 로 적은 것입니다. **둘 다 검증이 잡아 사람 확인으로 넘어갔고**, 조용히 통과한 것은 없습니다.
- 코드 검증으로 못 잡는 유형도 있습니다: "OO대학교 대학원" 의 "대학원" 을 전공 칸으로 옮김 (값이 원문에 있음). 원문과 필드를 나란히 보는 검수 화면에서 잡아야 합니다.
- 개발 세트에서 보류 세트로 넘어가도 정확도가 같거나 좋았습니다 → 개발 세트를 보고 고친 팩이 그 세트에만 맞춘 것은 아닙니다.
- OCR 줄 순서는 세로 중심 기준(`reading_order: center`)으로 측정했습니다. 영수증 방식(위쪽 기준)으로 바꾸면 표 양식에서 옆 칸 "신장/체중" 이 주소에 끼어 검증을 통과한 사례가 나와(2026-09-27 재측정), 팩마다 측정한 방식을 쓰도록 했습니다.
- 반복 3회(개발 세트): 회차 간 완전 일치 DOCX 95.8% · PDF 91.7% · 스캔 83.3%, 정확도는 비슷했습니다.

### 조건

1. **검증을 끄지 않습니다.** 지어낸 값은 생기지만 모두 검증이 잡았습니다.
2. **모든 문서를 사람이 검수합니다.** 검증을 통과해도 자동 승인하지 않습니다 (코드로 못 잡는 유형이 있음).

## 영수증 (receipt)

**합격** · 팩 v1.0.0 · gemma4:12b · KORIE 영수증 150장 · 2026-09-25 ~ 26

| 지표 | 결과 |
|---|---|
| 합계 일치 (결제 금액 · 할인 전 합계 중 하나) | 96.5% |
| 검증 통과 (사람 확인 없이 끝난 비율) | 92.7% |
| 지어낸 금액 (인쇄되지 않은 수량×단가 값) | 1건 |
| 작업 시간 중앙값 | 14.9초 |

- 모델 선정 과정과 OCR 설정 문제는 [모델 선정 리포트](model_selection.md)와 [README](../README.md)에 있습니다.
- 영수증 추출을 Engine 과 팩으로 옮긴 뒤 같은 150장을 다시 처리해, 옮기기 전과 결과가 같음을 확인했습니다.
- 검증(합계 · 품목 합 · 사업자등록번호 · 원문 근거)에 걸린 문서만 사람이 확인합니다.
- 영수증은 이력서처럼 합격 기준을 먼저 정해 두고 잰 것이 아닙니다. 모델 선정 측정 결과(검증 통과 92.7%, 지어낸 금액 1건)를 보고 합격으로 정했습니다 (2026-09-26). 새 모델 · 팩 버전을 넣을 때는 기준을 먼저 정하고 다시 잽니다.
