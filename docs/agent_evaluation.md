# 로컬 LLM 에이전트 평가 리포트 (실험 분석 에이전트)

- 작성: 2026-09-26
- 대상 모델: `gemma4:12b`, `qwen3-vl:8b-instruct`, `qwen3-vl:8b`, 기준선 `qwen3:4b-instruct`, Ollama 0.34.4, RTX 5080 16GB
- 프레임워크: Microsoft Agent Framework 1.22 (`Microsoft.Agents.AI`, `Microsoft.Agents.AI.Workflows`), OllamaSharp 5.4
- **결론: 모델이 도구 호출 순서를 스스로 정하는 에이전트는 로컬 8~12B 모델로는 믿을 수 없다 (보류 세트 64~73%).**
  **순서를 코드로 고정하고 LLM 에게 질문 해석과 문장만 맡기면 91%, 지어낸 값 0, 반복 실행 결과 100% 일치.**
  **이 도구에는 도입하지 않는다.** 실험 수가 적어 화면으로 충분하고, 좋아진 이유가 프레임워크가 아니라 설계였기 때문이다.

## 1. 왜 시도했나

도입 검토에서 "로컬 모델로 에이전트 업무(여러 단계 조회, 도구 사용)도 되나?"를 자주 묻는다. 이 도구에서 사람이 손으로 하던 **결과 해석** 단계를 대상으로 삼았다.

```
문서 업로드 ➔ 조합 실험 실행 ➔ 채점·점수 ➔ [결과 해석] ➔ 판단 (모델 선정·설정 적용)
   사람          코드 (자동)      코드 (자동)    사람이 손으로     사람
```

결과 해석은 점수만으로 판단이 안 될 때 틀린 문서를 열고, 추출 값과 OCR 원문을 대조해 원인을 찾는 일이다 (README 의 OCR 줄 방향 문제, 오답 21건 분류가 여기서 나왔다). 에이전트에게는 **읽기 전용**으로 이 조회·대조·집계만 맡기고, 실험 실행과 설정 적용은 맡기지 않았다.

## 2. 측정 방법

- **도구 7개** (API GET 을 감쌈): 실험 목록 · 실험 상세 · 조건별 문서 목록 · 추출 결과 · OCR 텍스트 · OCR 근거 확인(값이 원문에 있는지 코드로 대조) · 프롬프트
- **과제**: 개발 세트 30개 (도구 한 번 10 · 여러 단계 10 · 도구로 알 수 없음 5 · 오류 복구 5), **보류 세트 15개**
  - 보류 세트는 워크플로를 만들기 전에 작성하고, 측정 때 처음 돌렸다. 개발 세트는 실패를 보며 설계했으므로 개발 세트로만 재면 낙관적이다 (RAG 리포트에서 예시가 개발 세트에서는 좋고 보류 세트에서 나빴던 교훈)
  - 함정 과제 포함: README 에만 있는 숫자를 묻기, 쓰기 도구가 없는데 설정 적용을 요청, 원문에 **없는** 날짜 확인
- **채점** (`eval/agent_eval.py`): 필요한 도구를 불렀는지, 답에 정답 표현이 있는지, 금지 표현이 없는지. **근거 없는 숫자**: 답의 숫자가 질문·도구 결과 어디에도 없으면 셈 (비율 ×100, 반올림 허용)
- 과제마다 **3회 반복** (temperature 0 이어도 결과가 흔들림), 3회 모두 같은 결과인 과제 비율을 "반복 일치"로
- 정규식 채점은 첫 측정에서 틀린 판정이 나온다. 0/3 과제와 모델별로 갈리는 과제를 원문으로 확인해 개발 세트 기준을 7건 고쳤고 (모든 설정에 같이 적용), **보류 세트 기준은 결과를 본 뒤 바꾸지 않았다**

## 3. 1차: 모델이 도구 호출을 스스로 정하는 에이전트

개발 세트 30 × 3회. 성공률은 도구 한 번 + 여러 단계 과제 기준

| 설정 | 성공률 | 여러 단계 | 근거 없는 숫자 | 반복 일치 | 시간 중앙값 |
|---|---|---|---|---|---|
| gemma4:12b | **85%** | 70% | 1 | 83% | 3.8초 |
| qwen3-vl:8b-instruct | 75% | 60% | 0 | **100%** | 1.6초 |
| qwen3:4b-instruct (기준선) | 55% | 20% | 0 | 93% | 1.2초 |
| gemma4:12b + think | 75% | 53% | 3 | 80% | 8.3초 |
| qwen3-vl:8b (추론형) | 87% | 87% | 4 | 87% | 31초 |

- 도구를 한 번 쓰는 과제는 gemma4 가 30/30. **여러 단계에서 무너진다**
  - 목록의 문서마다 이유를 조회해야 하는 과제는 **다섯 설정 모두 0/3** (첫 문서만 보거나 목록 정보로 추측)
  - 실험 id 를 옮겨 적다 한 글자를 빠뜨리고, 도구가 "찾을 수 없음"을 돌려주자 "틀린 파일은 없다"고 결론을 지어냄
  - 문서 목록을 조회하지 않고 일치율로 역산하다 틀림
- **think 를 켜면 오히려 지어냄**: 실험 id "10, 9, 8…", 파일명 "101, 102, 103", README 에만 있는 값을 묻는 함정에 "40건"
- 추론형 qwen3-vl:8b 는 여러 단계가 가장 좋지만 추론이 폭주해 문맥 한도에 12번 걸림 (최대 235초)
- 도구 설계가 결과를 바꿈: 이름만 있는 지표(`passedWrongAny`)는 잘못 읽혀 설명을 붙였고, "28,900" 과 28900 대조를 LLM 에 맡기면 틀려 **코드 대조 도구**를 만들었다

**Ollama 도구 호출에서 확인한 것**
- JSON 스키마 강제(`format`)와 도구를 같이 주면 모델이 도구를 부르지 않고 JSON 으로 답을 지어낸다 ➔ 도구를 쓰는 턴에서는 `format` 을 쓰지 않는다
- 문맥 길이(`num_ctx`)가 빠지면 기본 4096 에서 답이 잘려 "빈 답 · 끊긴 답 · 실행마다 다른 경로"처럼 보인다 (개발 중 실제로 겪음, 원시 요청을 기록해 찾음)

## 4. Agent Framework 로 옮기면 달라지나

- 같은 도구·프롬프트·옵션으로 `ChatClientAgent` 를 쓰면 gemma4 **86% vs 86%** (직접 만든 루프와 같음), 시간 3.7 vs 3.8초 ➔ 프레임워크는 품질을 바꾸지 않는다
- **사람 승인**: 쓰기 도구(프롬프트 버전 저장, 실제로는 기록만 하는 dry-run)를 승인 필요 도구로 두면, 거절 시 실행 0건 · 승인 시 1건으로 게이트는 동작한다
  - 그러나 **거절한 3번 모두 모델이 "새 버전을 저장했습니다"라고 답했다** ➔ 쓰기 결과는 모델 답이 아니라 코드가 기록한 실행 여부로 보여 줘야 한다

## 5. 2차: 순서는 코드, LLM 은 해석과 문장만

```
질문 ➔ 라우터 (LLM, JSON 스키마, 도구 없음) ➔ 실험 이름 ➔ id (코드) ➔ 의도별 실행기 (코드: 조회 · 반복 · 계산)
     ➔ 요약 (LLM: 조회 결과 ➔ 한국어) ➔ 대조 (코드: 답의 숫자·파일명·id 가 조회 결과에 있는지, 아니면 템플릿 답)
     실험 이름이 여러 개와 맞으면 되묻기
```

1차 실패를 하나씩 코드로 옮겼다: 문서마다 조회는 코드 반복, id 는 코드가 목록에서 찾음, 수·차이·% 는 코드가 계산, 지어낸 값은 대조로 걸러냄

- **라우터**: 의도 9개로는 "실험 문서" 질문을 셋 중 어디로 보낼지 헷갈렸다 (87~90%). 셋을 하나로 합치고 구분(이유 조회, 원문 대조)을 코드로 옮기자 93%, 3회 반복 100% 일치. 95% 를 맞추려고 개발 세트를 보며 프롬프트를 더 다듬지는 않았다 (과적합)

**결과** (3회 반복, 성공률은 도구 한 번 + 여러 단계 과제 기준)

| 설정 | 세트 | 성공률 | 근거 없는 숫자 | 반복 일치 | 시간 중앙값 |
|---|---|---|---|---|---|
| gemma4:12b 자유 루프 (1차) | 개발 | 85% | 1 | 83% | 3.8초 |
| **gemma4:12b 워크플로** | 개발 | **100%** | **0** | **100%** | 4.0초 |
| qwen3-vl:8b-instruct 워크플로 | 개발 | 82% | 0 | 93% | 1.9초 |
| gemma4:12b 자유 루프 (1차) | **보류** | 73% | 1 | 73% | 4.1초 |
| **gemma4:12b 워크플로** | **보류** | **91%** | **0** | **100%** | 3.7초 |
| qwen3-vl:8b-instruct 자유 루프 (1차) | 보류 | 64% | 0 | 87% | 1.7초 |
| qwen3-vl:8b-instruct 워크플로 | 보류 | 91% | 0 | 100% | 2.0초 |

- 보류 세트에서 자유 루프 64~73% ➔ 워크플로 91%. 반복 일치 100%, 속도는 비슷
- 요약이 조회 결과와 맞지 않아 템플릿 답으로 바꾼 경우는 gemma4 0/135 ➔ 요약 LLM 이 사실을 제대로 옮겼다
- instruct 는 라우터 정확도는 gemma4 와 같았지만(93%) 요약에서 항목을 빠뜨리거나 조건을 잘못 옮겨 개발 세트 82% ➔ 요약은 gemma4 가 낫다
- 보류 세트 실패는 한 과제 (라우터가 "실험의 두 번째 문서"를 작업 단위 질문으로 해석). 이때도 "작업 id 가 없어 확인할 수 없다"고 답했고 값을 지어내지 않았다

## 6. 도입하지 않는 이유

| 이유 | 근거 |
|---|---|
| 지금 규모에서는 화면으로 충분 | 실험 8개, 에이전트가 답하는 질문 대부분이 실험 화면에서 1~2분. 에이전트는 새 정보를 만들지 않고 있는 정보를 찾아 줌 |
| 좋아진 이유는 프레임워크가 아니라 설계 | 자유 루프는 직접 구현이든 Agent Framework 든 86%. 91% 는 순서를 코드로 고정해서 나옴 (일반 코드로도 같은 결과) |
| 결정은 어차피 사람 | 실험 실행 · 설정 적용은 맡기지 않음 (승인 거절 후 "저장했다"는 답) |

도입한다면 이렇게: **순서는 코드로 고정, LLM 은 질문 해석과 문장만, 답의 값은 코드로 대조, 쓰기는 승인 + 코드 기록으로 표시, think 는 끔**. 문서 파이프라인의 원칙(LLM 은 구조화, 검증은 코드)과 같다.

## 7. 한계

- 과제 45개, 실험 8개 규모. 실험·문서가 수백 개로 늘면 조회를 대신하는 가치와 실패 양상이 달라질 수 있다
- 코드 대조는 **지어낸 값은 잡지만 빠뜨린 값은 못 잡는다** (instruct 워크플로가 CNN 오답 파일 3개 중 2개만 적은 경우)
- 보류 세트 한 과제(instruct)는 내용은 맞았으나 파일명·값을 적지 않아 사전 기준으로 실패 처리
- 과제의 실험·작업 id 는 이 환경의 DB 기준이라, 다른 환경에서는 과제를 다시 써야 한다

## 8. 재현

코드는 측정 재현용으로 `spikes/AgentSpike` 에만 있다 (API · 화면에 넣지 않음, CI 빌드 대상 아님). API(`:5000`)와 Ollama 가 떠 있어야 한다.

```bash
dotnet run --project spikes/AgentSpike -- run eval/agent/tasks.json eval/results/agent/spike1.jsonl --configs gemma4:12b,gemma4:12b@af,gemma4:12b@wf --reps 3
src/OcrService/.venv/Scripts/python eval/agent_eval.py --run spike1
```

- 설정 이름: `모델` = 자유 도구 루프, `+think` = 추론 켬, `@af` = Agent Framework ChatClientAgent, `@wf` = 워크플로
- 보류 세트: `eval/agent/tasks_holdout.json` (채점 시 `--tasks eval/agent/tasks_holdout.json`)
- 라우터만 측정: `dotnet run --project spikes/AgentSpike -- route-eval eval/agent/tasks.json <out.jsonl> --configs gemma4:12b --reps 3`
